# InvSee++ Folia 26.2 / 26.3：管理员说明

> 候选版本 `0.31.23-folia.1-rc2`。已完成指定 Folia 26.2 / 26.3 构建的跨区域与离线测试，但不能保证所有第三方插件组合、硬件故障或未来版本绝对安全。先在备份后的测试环境验证，再部署。

## 适用范围

这是为 Folia 单独实现的模块，沿用原项目许可与署名。它不使用旧版共享实时背包的实现，也不兼容旧版 InvSee++ API。不要与旧版 InvSee++ 或其附属插件同时安装。

当前目标为 Minecraft / Folia **26.2 和 26.3、Java 25**。实测官方 Folia 26.2 build 7 BETA 和 26.3 build 6 ALPHA。两者自身的发布级别不是本插件的稳定性承诺。后续 Minecraft 版本需要重新检查 API、NBT 和服务端行为并完成验收；不能通过修改版本判断来获得可靠兼容性。

构建步骤、依赖校验和已知构建限制见 [BUILDING.md](BUILDING.md)。不要将 Minecraft 服务端依赖打包进插件或提交到仓库。

## 安装

1. 正常停服，备份世界 `playerdata` 与插件数据。
2. 移除旧版 InvSee++ 及其附属插件，只放入本包的 `InvSee++-Folia.jar`，不要同时加载两套实现。
3. 使用 Java 25 启动受支持的 Folia 版本，确认插件启用及日志无数据/恢复错误。
4. 给可信管理员分配必要权限；离线访问还需显式授予对应绕过豁免权限。先用测试账号验证在线与离线读写。

不要热重载插件。其他版本会拒绝启动，不能靠改版本字符串绕过验证。测试记录见 [最新运行记录](../test-harness/PARITY_RESULTS.md)，构建和依赖见 [BUILDING.md](BUILDING.md)。

## 使用方法

- `/invsee <玩家名或 UUID>`：查看玩家背包。
- `/endersee <玩家名或 UUID>`：查看末影箱。
- `/invseerecovery [交易 UUID]`：列出未解决交易，或查询指定交易的状态、来源、目标与说明。
- `/invseerecovery claim <原交易 UUID>`：仅认领日志能够证明尚未交付、确实由插件保管的物品。通过新的持久化交易放入操作管理员的空存储槽，不是任意交易的补发命令。

打开界面前清空鼠标光标上的物品。界面展示目标背包的副本，而不是允许原版容器直接操作目标玩家的物品。目标仍然可以活动，提交修改时必须再次校验槽位；状态发生变化时操作可能被拒绝，需要刷新后重试。

交互先选择来源，再选择另一侧的目标槽位。左键选择整组，右键选择半组；目标可以是空槽或有容量的同类物品堆，物品组件必须兼容。Shift 尝试转入另一侧第一个可用槽位；容量不足时不会越过堆叠上限。数字键和副手键支持空槽或兼容堆叠的转移，不执行两组不同物品的直接交换。

拖拽、丢弃、创造模式复制等未实现动作会被明确拒绝，不会退回原版容器搬运逻辑。装备放入根据服务端物品的可装备组件校验槽位、玩家类型和数量，不能把任意物品强行塞入护甲槽。鼠标光标和合成格不在管理范围内。这些是明确的功能限制，不能把当前模块视为旧版全部功能的等价替代。

在线目标界面约每秒刷新一次，并合并重叠的刷新请求；离线界面不会以固定频率反复读盘。选择来源只是选择，不意味着已经锁定物品，提交时仍会校验最新状态。

离线名字首先使用服务端已知缓存，再使用有界的本地玩家数据索引，不向名字查询服务发起联网请求。未知名字、重复的历史名字或无法验证的数据必须使用准确 UUID；本模块不会为从未加入的玩家凭空创建完整玩家档案。

离线读取要求存在可识别、受支持的玩家数据。损坏、版本不匹配、正在登录、另一个编辑会话占用或有未解决事务时，拒绝管理员打开离线编辑，不覆盖文件。不要手工改写正在被插件使用的 playerdata。

**玩家登录优先**：玩家开始登录时，管理员的离线界面会自动失效并关闭，不再因为管理员开着界面而要求玩家退出重试。尚未开始的编辑被取消；已经接受的事务（包含可能的回滚和保存确认）完成后，登录流程才读取玩家数据。等待只发生在异步登录阶段，不阻塞区域线程。玩家上线后，管理员可重新打开在线背包，双方仍可修改；槽位冲突会拒绝旧操作并刷新。

正常交接不需要人工解除锁定。存储故障、未解决的恢复记录或超过 15 秒的异常交接仍会明确报错，不能为强行放行而让登录读取未保存完整的数据。这与“管理员开着界面就不让进服”不同。

## 管理命令

- `/invgive <目标> <物品类型> [数量]`、`/endergive <目标> <物品类型> [数量]`：添加物品，默认 1 个。
- `/invclear <目标> [物品类型] [数量]`、`/enderclear <目标> [物品类型] [数量]`：按条件清理。省略类型和数量会清空对应管理范围，包括背包装备槽。
- `/invclone <来源> [目标]`、`/enderclone <来源> [目标]`：读取来源快照并替换目标对应管理范围。游戏内省略目标使用执行者；控制台必须指定目标。

Give、clear 和 clone 有意增加、删除或复制物品，请先确认目标。每条命令记录完整前后快照，再在目标所属线程校验并提交；准备期间目标发生变化时拒绝旧快照覆盖。Give 容量不足会整条拒绝，不会静默丢弃剩余物品。Clone 使用读取时的来源快照，不会冻结或持续同步来源玩家。

当前 give 只支持物品类型和数量，不接受旧附属插件的 NBT / 数据组件参数；多余参数会报错，不会被静默忽略。旧版附属插件 API、多世界背包集成仍不兼容。

## 权限

| 权限 | 用途 |
| --- | --- |
| `invseeplusplus.invsee.view` | 查看背包 |
| `invseeplusplus.invsee.edit` | 修改背包 |
| `invseeplusplus.endersee.view` | 查看末影箱 |
| `invseeplusplus.endersee.edit` | 修改末影箱 |
| `invseeplusplus.exempt.invsee` | 目标免于背包查看 |
| `invseeplusplus.exempt.endersee` | 目标免于末影箱查看 |
| `invseeplusplus.bypass-exempt.invsee` | 绕过背包豁免检查 |
| `invseeplusplus.bypass-exempt.endersee` | 绕过末影箱豁免检查 |
| `invseeplusplus.recovery` | 查询恢复信息 |
| `invseeplusplus.give.inventory` / `invseeplusplus.give.enderchest` | 对应的 give 命令 |
| `invseeplusplus.clear.inventory` / `invseeplusplus.clear.enderchest` | 对应的 clear 命令 |
| `invseeplusplus.clone.inventory` / `invseeplusplus.clone.enderchest` | 对应的 clone 命令 |

默认查看、编辑、恢复权限授予 OP；豁免与绕过权限默认不授予。离线时无法可靠查询任意权限插件的状态，因此离线访问还要求对应的 `bypass-exempt` 权限。只给可信管理员分配编辑与绕过权限。

保留 `invseeplusplus.view`、`.edit`、`.exempt`、`.bypass-exempt` 及 `invseeplusplus.give.*`、`invseeplusplus.clear.*`、`invseeplusplus.clone.*`、`invseeplusplus.*` 的显式子权限。总通配节点包含豁免、绕过和管理权限，应谨慎授予；恢复权限仍单独分配。未实现的 reload、旧 tabcomplete/API 不因此获得兼容能力。

## 异常与恢复

交易使用预写日志，离线文件修改使用原子写入和恢复记录。**插件日志与 Minecraft 两个玩家的数据文件不能形成一个跨文件原子事务**：强制杀进程、磁盘故障或断电时仍可能出现结果不确定的时间窗口。实现保留不确定记录并阻止相关操作，不会根据一条旧日志盲目补发物品。

遇到恢复提示时：

1. 暂停受影响玩家的背包管理操作，记录交易 ID、玩家 UUID、时间与完整服务端异常。
2. 保留插件数据目录和世界 playerdata。需要人工检查时先正常停服，再复制备份，避免读取正在变化的数据。
3. 检查交易来源、目标、状态、对应槽位及正常游戏过程中可能发生的移动。不要仅凭来源槽位为空认定物品丢失。
4. 未确认物品实际位置前，不执行 `/give`、回滚 playerdata 或重复交易。日志中的待恢复物品可能已经到达目标。
5. 只有报告明确属于可认领保管物品的交易，才使用 `claim`；先准备一个空存储槽。结果不确定的交易不能认领，必须人工核对。不要删除事务日志来“解除锁定”，也不要修改日志内容或直接解码后当作可补发清单。恢复必须同时核对双方数据；保留原始证据。

正常停服比强制终止安全。生产使用前备份世界与插件数据；不要使用插件热重载工具作为日常升级方式。未完成的持久化操作可能需要等待，不能通过忽略错误来提前宣称保存成功。

## 性能与验收

持久化队列有容量限制。高并发或磁盘变慢时，拒绝或延后操作优于无限积压。异步执行并不意味着零成本；每笔交易的持久化会增加延迟，应记录实际测试服的吞吐、延迟分位数和区域线程耗时。

最低验收包含：不同区域的多个管理员同时编辑、目标移动同一槽位、传送、退出与重连、权限撤销、关闭界面、禁用插件、离线编辑与登录竞争、磁盘失败、重启，以及物品总数和组件保持不变。合成线程测试不能替代真实 Folia 玩家测试；通过协议转换连接的客户端也必须在报告中注明。

具体通过和未运行的项目应以最终测试报告为准。任何未来版本、第三方背包管理插件或未覆盖的热重载场景都不能自动继承本版本结论。
